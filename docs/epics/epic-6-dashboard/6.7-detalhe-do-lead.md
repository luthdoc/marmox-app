# Story 6.7: Detalhe do Lead

**Epic:** 6 — Dashboard
**Status:** pending

## User Story

As a marble company owner,
I want to view a lead's full conversation history and their qualified data on a single screen,
so that I can understand the context before calling or visiting the client.

## Acceptance Criteria

1. A rota `/dashboard/leads/[id]` existe e exibe os dados do lead identificado por `[id]`.
2. O Supabase client usado na busca usa o JWT do usuário logado (não service key); nenhuma query bypassa o RLS.
3. O response contém apenas campos do tenant autenticado — se o lead não pertencer ao tenant autenticado, a página retorna 404 (o RLS naturalmente retorna zero rows; o frontend trata isso como "not found").
4. A seção de dados qualificados exibe: nome, telefone (mascarado conforme Story 6.6), serviço desejado (`service_type`), material (`material`), urgência (`urgency`), bairro (`neighborhood`), status (via `StatusBadge`), e data do último contato formatada.
5. A seção de conversa exibe todas as mensagens da tabela `messages` associadas ao lead (via `conversations.lead_id = lead.id`), ordenadas por `created_at` ascendente.
6. Cada mensagem exibe: conteúdo (`content`), direção (`inbound` alinhado à esquerda, `outbound` alinhado à direita) e horário formatado (HH:mm).
7. Mensagens com `media_url` não-nula exibem um link "Ver mídia" que abre a URL em nova aba — não tenta renderizar a mídia inline no MVP.
8. A conversa é somente leitura — não há campo de input para enviar mensagens.
9. Existe um botão "Voltar" que navega para `/dashboard/leads`.
10. Estado de lead não encontrado exibe mensagem "Lead não encontrado." com link para voltar à lista.
11. A página é responsiva e operável no celular.
12. `npm run typecheck` e `npm run lint` passam sem erros.

## Technical Notes

> Leia `node_modules/next/dist/docs/` antes de implementar — breaking changes nesta versão afetam rotas dinâmicas (`[id]`), como `params` é acessado em Server Components e o comportamento de `notFound()`.
>
> A query de mensagens requer join: `conversations` onde `lead_id = id`, depois `messages` onde `conversation_id IN (...)`. Alternativamente, se houver apenas uma conversa por lead no MVP, buscar `conversations` filtrando por `lead_id` e pegar o primeiro resultado. Verificar o schema gerado na Epic 2.
>
> O RLS garante que a query de lead retorna zero rows se o `tenant_id` não corresponder ao usuário autenticado. O frontend deve verificar se o resultado é null/vazio e renderizar 404 nesses casos — não depender de error throw do Supabase.
>
> LGPD (NFR6): esta tela exibe dados pessoais do lead. Não implementar deleção nesta story — é um requisito separado fora do escopo do MVP, mas registrar nos ACs que os dados são exibidos apenas para o tenant dono.
