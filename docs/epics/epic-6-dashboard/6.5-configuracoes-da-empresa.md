# Story 6.5: Configurações da Empresa

**Epic:** 6 — Dashboard
**Status:** completed

## User Story

As a marble company owner,
I want to view and edit my company's configuration (name, services, regions, working hours, welcome message) directly on the page without modals,
so that I can keep the agent's information up to date with minimal friction.

## Acceptance Criteria

1. A rota `/dashboard/configuracoes` existe e exibe os dados atuais do tenant autenticado: nome, serviços (`services[]`), regiões (`regions[]`), horários de funcionamento (`working_hours`) e mensagem de boas-vindas (`welcome_message`).
2. O Supabase client usado na busca usa o JWT do usuário logado (não service key); nenhuma query bypassa o RLS. A query filtra por `auth.uid()` implicitamente via RLS — não é necessário filtro explícito de `tenant_id` no frontend.
3. O response contém apenas campos do tenant autenticado — RLS garante isso; o frontend não exibe nem armazena dados de outros tenants.
4. Os campos são inline editáveis: ao clicar em um campo, ele se torna editável (input/textarea) sem abrir modal. Ao sair do campo (blur) ou pressionar Enter, a edição é salva automaticamente via `UPDATE` no Supabase.
5. `services[]` e `regions[]` são editáveis como texto separado por vírgulas (serializado/desserializado pelo frontend ao ler e salvar).
6. Todo input é validado antes de ser processado: `name` não pode ser vazio; `services` e `regions` devem ter ao menos um item não-vazio após parse.
7. Erro de salvamento é exibido inline próximo ao campo, sem fechar o modo de edição.
8. Feedback visual de "salvo" é exibido brevemente após salvar com sucesso (ex: texto "Salvo" por 2s).
9. A página usa Card (border-radius 18px) do design system para agrupar os campos. Sem sombra, sem gradiente.
10. A página é responsiva e operável no celular.
11. `npm run typecheck` e `npm run lint` passam sem erros.

## Technical Notes

> Leia `node_modules/next/dist/docs/` antes de implementar — breaking changes nesta versão afetam Server Actions, revalidação de cache e como dados são carregados em Server vs Client Components.
>
> A busca inicial dos dados do tenant pode ser feita em Server Component (usando server client) para evitar flash de conteúdo vazio. A parte de edição inline requer Client Component.
>
> A coluna `working_hours` no banco é do tipo text/jsonb (verificar schema da Story 2.1). Editar como textarea de texto livre é suficiente para MVP se for text; se jsonb, serializar/desserializar como JSON string.
>
> Para o padrão de edição inline sem modal: considerar um componente `InlineField` que alterna entre modo leitura e modo edição internamente, recebendo `value`, `onSave(newValue)` e `validate(value)` como props.
